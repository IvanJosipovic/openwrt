# TP-Link Festa F65-Wall v1: port research and implementation status

**Research date:** 2026-11-03
**Scope:** software/public-source research plus user-run, read-only stock terminal inspection; no direct authenticated session, physical board inspection, or firmware modification.
**Working branch:** `add-festa-f65-wall`
**Upstream baseline:** `upstream/main` at `46e6335fbd3b825008a39758a45fa97a39814e3b` (`realtek: rtl931x: re-add missing config symbol`). Local `main` is an ancestor of this commit, and `add-festa-f65-wall` has been rebased onto it.

**Upstream name check:** Upstream already supports a device marketed as `TP-Link F65 v1`, merged in commit `7449064f64` (PR #22138), but that is the **ceiling-mount Festa F65** with MediaTek MT7981B/MT7976. Its DTS is `target/linux/mediatek/dts/mt7981b-tplink-f65v1.dts` and compatible is `tplink,f65-v1`. This project is the distinct **Festa F65-Wall** with live-confirmed Qualcomm IPQ5018/QCN6122 and RTL8367S; the ceiling model's recovery, radio, storage, and wiring details do not apply.

This is an evolving research and implementation report, not an installability claim. The stock runtime has been inspected through the Festa controller terminal, but the physical board and bootloader have not. Treat vendor GPL code as evidence about the vendor build, not as proof that the shipped US v1.0 unit matches every setting in that build.

## Summary and recommendation

The initial F65 DTS, image recipe, factory-data mount, calibration hooks, and network defaults are implemented and build. The generated FIT, factory UBI, and sysupgrade images have not been booted. The live unit's device-tree model reports `Qualcomm Technologies, Inc. IPQ5018/AP-MP03.3`, confirming the SoC/platform and matching TP-Link's F65-Wall v1 GPL source. REA analysis of the exact stock SSDK module recovers switch-management MDIO PHY address 29 and the GPIO39 reset pulse used at module initialization. The external DSA node and port labels remain untested; regional Wi-Fi board-data and bootloader recovery also remain unresolved.

The official stock update package contains a 60,540-byte standalone DTB that matches the runtime model and compatible and confirms four MDIO1 PHY declarations plus the QCA83xx-labeled switch configuration. FCC internal photos identify the external switch as RTL8367S. REA reverse-engineering of the exact-build `qca-ssdk.ko` identifies SSDK device ID 1, switch-management PHY address 29 (`0x1d`), and a GPIO39 high-low-high reset pulse at module initialization, matching the DT's `reset_gpio = <0x27>`. GPIO39 is also declared as the active-high 5 GHz LED, so the physical net sharing remains unresolved. The draft still omits an external DSA node pending safe nonpersistent validation of the CPU link and port map. Runtime logs and the vendor startup script confirm the 2.4 GHz IPQ5018 and 5 GHz QCN6122 radios and their calibration-file mapping. Stock region-specific BDFs remain unlicensed/unpackaged for this port. The live MTD table matches vendor NAND metadata. No safe RAM-boot or persistent-install method is verified.

The EAP655-Wall is a useful **vendor-software reference**: its separate official GPL bundle independently selects IPQ5018 MP03.3, 512 MB DDR, RTL8367S, two radios, and switch-reset GPIO39. The F65 stock SSDK binary now independently shows a GPIO39 reset pulse. These are matching software settings, but they do not prove identical PCB or interchangeable port, radio, flash, calibration, LED, or bootloader behavior. The F65 DTS also assigns GPIO39 as the 5 GHz LED; whether that pin is shared electrically or the LED property is stale still needs physical/runtime verification.

## Initial OpenWrt approach

1. Keep the base at current upstream `main` and use existing `qualcommax` / `ipq50xx` support.
2. Establish the exact stock board identity and dump DTB, kernel logs, `/proc/mtd`, `/proc/partitions`, `/proc/cmdline`, network interfaces, loaded switch/Wi-Fi modules, and boot environment using read-only access.
3. Back up factory, radio/calibration, identity, and boot-environment data before attempting any non-stock boot. Verify hashes and keep unique data private.
4. Use the stock-derived MDIO address 29 and GPIO39 reset pulse as candidate DSA parameters. Validate the CPU link, DSA port labels, physical PHY/jack map, GPIO39/LED sharing, and pass-through PoE circuitry before treating the configuration as tested or enabling port power control.
5. Identify a documented bootloader RAM-load route. Only then prepare an initramfs for a nonpersistent boot. Do not construct a flashable image based on the current partition-table alone.
6. Build a clean board DTS from verified facts, use upstream drivers and firmware packaging, and add only a board-specific image definition once Ethernet, radio, calibration, and recovery assumptions are grounded.

### RAM boot outlook

IPQ5018 is an upstream-supported platform, and vendor material shows a Qualcomm vendor boot stack, so a RAM-loaded image may be technically possible. There is currently no evidence for this device's bootloader type/version, serial access, signature policy, TFTP/recovery mode, accepted image format, or safe load addresses. Therefore RAM boot is **plausible but unverified**. Do not interrupt the bootloader or issue commands until UART voltage/pinout, bootloader identity, and recovery behavior have been established.

See [flash-layout.md](flash-layout.md) for the vendor/live partition comparison and official signed-image analysis, [device-tree.dts](device-tree.dts) for the DTB extracted from that image, and [bootloader-recovery.md](bootloader-recovery.md) for APPSBL findings and the evidence required before a nonpersistent boot attempt.
